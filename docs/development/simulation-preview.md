# VMware Gazebo / RViz preview

This opt-in ROS 2 Jazzy / Gazebo Harmonic environment exercises local Linux
X11/XWayland graphics. The default Compose and Dev Container environment remains
available. The preview uses the same development service and Dockerfile, with a
separate `duk-jazzy-sim` Compose project so an existing notebook session is not
replaced.

## First launch

Run these commands from the repository root in a host desktop terminal, not from
inside the base development container. Docker Engine, Compose, Python 3 and
`xauth` must be available on the host. RViz, Gazebo and OpenGL diagnostic tools
are installed in the simulation image, not on the host.

```bash
python3 tools/dev/duk-dev.py configure --preset vmware
python3 tools/dev/duk-dev.py up
python3 tools/dev/duk-dev.py doctor
python3 tools/dev/duk-dev.py demo
```

The last command builds the two preview ROS packages and opens Gazebo and RViz.
Keep its terminal open. Use `stop` from another host terminal to end the launch;
`down` stops the isolated
simulation environment without deleting its named volumes:

```bash
python3 tools/dev/duk-dev.py stop
python3 tools/dev/duk-dev.py down
```

## Change graphics settings

`configure` saves settings under ignored `.local/simulation/`. Supplying only one
flag preserves the other settings. `auto` selects DRI when a render node exists;
this does not establish hardware acceleration. Inspect `doctor`'s renderer.
Failed preflight leaves the last saved settings and Compose override intact.
Concurrent `demo` commands are rejected before either can share build output.

```bash
python3 tools/dev/duk-dev.py configure --gpu software
python3 tools/dev/duk-dev.py up
python3 tools/dev/duk-dev.py demo
```

GPU choices are `auto`, `dri`, and `software`. GUI choices are `x11` and `none`.
Changing graphics settings recreates the container; the dependency image can be
reused. The host's numeric render-device group is added to the non-root user.
Software mode does not map `/dev/dri` and explicitly enables Mesa software
rendering. Ogre 1, disabled shadows, a compact world and a 20 FPS RViz setting
keep the initial test modest.

The simulation image removes Ubuntu Matplotlib's legacy `mpl_toolkits`
namespace bootstrap so Python's PEP 420 discovery can select the venv's matching
3D toolkit. Both system and venv Matplotlib 3D imports are checked; project Python
dependencies still come from the venv.

For a server-only test:

```bash
python3 tools/dev/duk-dev.py configure --preset headless
python3 tools/dev/duk-dev.py up
python3 tools/dev/duk-dev.py demo --headless
```

Restore desktop mode with `configure --preset vmware`. No host networking,
privileged mode, device-wide access or `xhost +` is used. Xauthority is prepared
for the current desktop session in a private runtime directory and mounted
read-only. The ROS domain is 42, discovery is localhost-only inside the
container, and Gazebo uses its own partition. This is not a physical-robot
network setup.

## VS Code Dev Containers

Select **Dev Containers: Reopen in Container**, then **DUK — VMware Simulation**.
If another configuration is already selected, use **Switch Container**. The
simulation configuration's host initialize command prepares the local override
and current Xauthority. It consumes the same Compose configuration as the CLI.
After changing flags, rebuild/reopen the simulation container. The original
**DUK — ROS 2 Development** configuration remains the base environment.

The helper rejects non-Jazzy configurations. NVIDIA, Jetson, Windows/macOS,
remote Docker and native Wayland forwarding are not implemented here. A Wayland
desktop can use its local XWayland server.

## Robot model and evidence boundary

The model has a rectangular illustrative body and two copies of the established
four-bar wheel leg. Both descriptions are generated by `duk_description` using
the [canonical geometry](../../robot/config/physical/duk_leg_geometry.json) and
the existing `duk_core` solver. Leg dimensions are never copied into a second
configuration:

- AB 131 mm, CD 135 mm, AD 81 mm;
- BC 42 mm, BH 119 mm, OH 55 mm;
- wheel diameter 150 mm;
- the configured topology and directed DA angle are preserved.

Planar x maps to ROS x and planar y maps to ROS z. Left and right legs differ
only by translation along ROS y. The body is 200 × 240 × 140 mm; leg planes are
290 mm apart. Link thicknesses, wheel width, body dimensions and colors are
illustrative, not physical specifications. H remains an auxiliary point.

The default pose is canonical linkage q = 75 degrees. A different reachable
snapshot can be selected at launch:

```bash
python3 tools/dev/duk-dev.py demo --angle-deg 90
```

Generated URDF, SDF, world and coordinate metadata are written under ignored
`data/generated/vmware-preview/`. Gazebo and RViz receive matching geometry. The
launch argument `output_dir` selects another output directory independently of
the `geometry` JSON path. The robot is explicitly **static**, with no mass,
inertia, actuators, controller,
gait or balance claims. Gazebo's `/clock` is bridged into ROS; RViz uses simulation
time. This smoke test does not validate closed-loop mechanism dynamics or wheel
contact behavior.

Geometry regression checks:

```bash
PYTHONPATH=robot/software/core/src:robot/software/ros2_ws/src/duk_description \
  python3 -m unittest discover \
  -s robot/software/ros2_ws/src/duk_description/test -v
```

Runtime observations are recorded in [Platform compatibility](../platforms/compatibility.md).

While the preview is running, verify the actual ROS integration from another
simulation-container shell after sourcing ROS:

```bash
source /opt/ros/jazzy/setup.bash
python /workspace/tools/environment-check/verify-simulation-preview.py
```

This requires the robot description, static world-to-base TF and advancing
simulation clock; it does not infer success just from running processes.
